Issue summary:
Customer reports repeated 'deadline exceeded' / truncated streaming responses when using very large max_tokens combined with a long conversation prefix. This occurs sporadically at the end of generation: client receives a partial stream then a terminal error rather than a final 'DONE' event.

Impact:
- Multiple paid API calls returning incomplete outputs for one enterprise customer on Dedicated capacity.
- User-visible failures for production document summarization pipelines (DocuScale).
- Repro rate ~30% for affected requests, higher during peak traffic windows.

Environment:
- Dedicated pool (gpu-pool-3) in prod/us-east.
- Requests authenticated with customer API key linked to DocuScale account.

Observed behavior:
- Streaming starts normally; tokens are emitted for a long time (minutes). Near the expected completion the stream stalls for ~20-120s then the client receives HTTP 504 or a 'deadline exceeded' close-frame. No explicit 5xx is seen mid-generation, and billing shows tokens consumed up to the last emitted chunk.

Expected behavior:
- For long-running generations, streaming should send final tokens and a terminal event (DONE) or a graceful fallback. The request should not be dropped mid-finalization for healthy Dedicated pools.

Steps to reproduce (customer-provided):
1) Use model redwood-alpha-13b-v2 with max_tokens=60000 and prefix size ~180k tokens (document + conversation).
2) Enable streaming over a persistent HTTP connection with client timeout set to 180s.
3) Trigger generation with a standard temperature=0.7.
4) Observe that in ~30% of attempts the stream stalls at the final flush and client receives deadline exceeded before final marker.

Logs / evidence:
- Customer curl logs (attached) showing partial streaming then 'curl: (56) Recv failure: Connection was reset' and a 504 from edge.
- Serving runtime traces (trace IDs): trace: 20260312-rt-9934 (attached) — shows finalizer task queued behind a burst of prefix-lookup KV cache evictions.
- Router / gateway logs show no immediate 5xx on token emission; 504 appears coming from the frontend gateway after a prolonged inactivity on the backend connection.
- Console graphs: CPU/gpu utilization normal for pool; however, there are short-lived spikes in RPC latency to KVS when requests hit heavy prefix windows.

Investigation notes (initial):
- Hypothesis 1: KV cache eviction + rehydration for very deep contexts causes the finalization task to be scheduled late on the worker, stretching the overall request duration beyond the gateway deadline.
- Hypothesis 2: Continuous batching policy holds onto finalization because of batch-window heuristics when max_tokens is huge; the worker waits for a small additional batch and delays final flush.
- Hypothesis 3: Edge/Load-balancer idle connection timeout triggers if no activity occurs for X seconds between token emission and final flush (observed gaps up to 120s).

Partial findings:
- Traces show finalizer worker step T_finalize had multiple preemptions and a median delay of 48s for affected traces vs 200ms for healthy traces.
- KV access latencies spiked from <10ms to 500-1200ms in the same traces; eviction churn correlates with long prefix sizes.
- Batching metrics indicate those requests were placed into an atypical 'tail' batch with a 10s batch-wait before finalization on some workers.

Customer impact and urgency:
- Customer pipeline has retries but deduplication is not perfect; partial outputs cause manual intervention. This is impacting an enterprise SLA. Marked Sev1 / P1.

Mitigation steps taken so far:
- Support set temporary per-customer server-side policy to cap max_tokens to 40k for DocuScale while we investigate. This reduced repro rate to <5%.
- Increased gateway idle timeout for the dedicated pool by 30s as a short-term mitigation.
- Engineering flagged relevant runtime nodes to disable long batch-window heuristics for the pool.

Proposed next steps:
1) Engineering: Pinpoint scheduling preemption — add instrumentation to measure queue wait times for finalizer stage and flag >5s. (Owner: Diego)
2) Runtime: Add a guard that short-circuits batch-wait for finalizer if outstanding tokens remaining < 5k or if per-request elapsed > 60s. (Owner: Runtime team)
3) Infra: Tune gateway idle timeout and ensure health checks won't kill in-progress streams in dedicated pools. (Owner: Platform)
4) Customer: Keep temporary token cap until a controlled rollout of fixes completes.

Notes on rollout and risk:
- Short-circuiting batch-wait is low-risk and can be rolled to a subset of dedicated pools first.
- Gateway timeout changes require coordination with infra and may affect other customers if global. We prefer pool-scoped configs.

Resolution expectation and timeline:
- Target: mitigations (batch short-circuit + instrumentation) in 2 weeks, gateway pool-scoped timeout adjustment in 1 week, followed by rollback of temporary token cap for the customer after verification.
