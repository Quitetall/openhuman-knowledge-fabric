Purpose:
This doc proposes a compact realtime socket protocol and SDK ergonomics for the Hosted API that emphasizes: minimal RTT for first tokens, typed/typed-delta frames for safe partial outputs, resilient tool-call semantics (idempotency and side-effect isolation), and clear telemetry hooks for quality monitoring. It targets mobile and web clients with intermittent connectivity, as well as server-side low-latency integrations.

Goals:
- Sub-50ms median handshake RTT for warm connections within a region.
- Typed partial output frames (schema-annotated) that allow clients to render incremental UI elements without full-parse risk.
- Deterministic ordering guarantees within a session fragment and graceful out-of-order reconciliation for resumed sessions.
- Tool-call contract that separates "intent" frames from "execute" frames to enable safe local simulation and replay.
- SDK primitives that make backpressure and reconnection simple for app developers.

Non-goals:
- This is not an attempt to replace the existing REST API; it's an opt-in path for low-latency streaming.
- We do not attempt to define an exhaustive schema language; we rely on JSON Schema v7 snippets for typed frames.

Success metrics (proposal):
- 95th percentile time to first partial frame <= 120ms (region warm).
- Reduction in customer-reported glitchy partial renders by 60% after client-side adoption of typed-delta frames.
- Decrease in support tickets related to tool-call duplicate side-effects after SDK-enforced idempotency primitives.

High-level proposal summary:
We introduce a small set of socket frame types sent over a secure WebSocket/TCP+TLS connection. Each frame is a JSON envelope with a light header and a typed payload. Frames are compact, suitable for incremental parsing, and include a small vector clock for per-session fragment ordering. The protocol supports: warm handshakes, resumable micro-sessions, prefix/KV caching hints, explicit backpressure tokens, and a two-phase tool-call flow (plan + commit).

Frame taxonomy (short):
- INIT: client -> server. Contains api_key (or token nonce), client_sdk, desired_response_schema (JSON Schema id or inline), client_time, resume_token optional. Server responds with INIT_OK or INIT_FAIL.
- INIT_OK: server -> client. Contains session_id, fragment_id, server_time, server_schema_override (if server applies normalization), and warm_path boolean.
- DELTA: server -> client. Typed partial content. Contains frame_id, parent_id, schema_ref, delta_path (JSON-Pointer), op (insert/replace/delete), content (typed), estimated_finality boolean.
- SNAPSHOT: server -> client. Full structured object for a given fragment_id (idempotent checkpoint).
- ACTION_INTENT: client -> server. *Non-committal* description of a desired tool call (tool id, args, call_id). SDKs should surface this to users for preview and local sim.
- ACTION_EXECUTE: client -> server. Signals commit for a previously sent ACTION_INTENT. Server treats execute frames as the point where side-effects may occur. ACTION_EXECUTE must reference call_id and include an idempotency_key.
- ACTION_RESULT: server -> client. Result of the tool call, includes call_id, status, typed_result, consumed_quota_hint.
- ACK: both ways. Lightweight acknowledgement of frame receipt; allows clients to garbage collect earlier frames.
- HEARTBEAT / PING: keepalive frames with minimal payload.
- ERROR: structured error frame with code, human message, and optional suggested_next_action.

Key protocol characteristics and rationales:
- Typed deltas: Clients provide a desired_response_schema at INIT. Server includes schema_ref on DELTA frames; clients can safely render typed snippets and progressively hydrate into richer UI components. Using JSON Schema snippet IDs keeps frame sizes small and enables incremental validation.
- Two-phase tool calls: ACTION_INTENT lets client preview what will be sent to a tool (search, send-email, mutate DB). Only when ACTION_EXECUTE is received does the server execute. This allows local confirmation flows and reduces accidental duplicates. ACTION_EXECUTE must include an idempotency_key; server will deduplicate within a configured window (default 24h).
- Resumability: Server issues resume_token in INIT_OK and periodic SNAPSHOT frames. If a client reconnects with resume_token and last_ack_frame_id, server replays missed deltas since last acknowledged snapshot or returns SNAPSHOT if deltas have expired. We keep retention small (configurable per tier) to limit memory.
- Backpressure: Server emits a backpressure_level on INIT_OK and may update it mid-session. Clients that observe increasing backpressure level should switch to "compact" schemas or reduce parallel ACTION_EXECUTE commits. SDKs will expose a simple backpressure callback and an adaptive send queue.
- Ordering: DELTA frames include incremental frame_id and parent_id. Server guarantees causal order within a fragment. Clients should apply frames idempotently (frame_id based) and use parent_id to detect missing frames for fetch/re-synchronization.

SDK ergonomics (recommendations):
- Surface a Connection object with methods: connect(), onDelta(cb), sendIntent(intent), commitIntent(call_id, idempotency_key), snapshot(), close(reason). Keep callback signatures simple: onDelta receives (typedPath, value, meta).
- Built-in local preview tooling: SDK should optionally run intent validators against local model/tool simulators. Default enabled for web SDK, opt-in for mobile to save size.
- Automatic replay helpers: SDK exposes a resume() helper that handles exponential backoff, token refresh, and a resume_token store. Developers should be able to plug their own storage for resume tokens (localStorage, secure storage).
- Backpressure APIs: onBackpressure(level) with levels: ok, constrained, congested. Provide helper to throttle outgoing ACTION_EXECUTE calls.
- Observability hooks: emit structured telemetry events for: handshake_latency, time_to_first_delta, intent_submit, execute_time, action_result_status, resume_success, unexpected_disconnect. These events should map to console-friendly logs and a structured event sink used by Console.

Security and safety notes:
- All frames must be sent over TLS; tokens should be short-lived and rotated via refresh flow.
- ACTION_EXECUTE frames with side-effecting scopes must include a least-privilege scope claim in INIT. Server will refuse execute if client scope insufficient.
- Tool results must include sanitized confidence hints and an optional provenance token to allow audit trails.

Rollout plan (sketch):
1) Internal alpha with web SDK and a single partner integration (search tool) behind a feature flag.
2) Collect telemetry, validate handshake latency and schema compatibility.
3) Add mobile SDK light bundle (no local simulators) and enable resumability.
4) Beta: open to customers with clear docs and migration guide.

Open questions / decisions needed:
- How long to keep delta retention for resumability per tier? (24h default? 72h for enterprise?)
- Idempotency window for ACTION_EXECUTE (configurable per tool?)
- Whether to allow server-initiated ACTION_INTENT for server-driven tool recommendations (needs separate auth model).
