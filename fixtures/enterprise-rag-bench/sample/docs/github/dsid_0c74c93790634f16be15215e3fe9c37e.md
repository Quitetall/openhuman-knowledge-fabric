description:
Context and motivation: Streaming TTFB spikes in mixed workloads remain a top customer pain point. Existing flush cadence + backpressure heuristics are reactive and cause microbursts when kernels are scheduled separately for adjacent microbatches. This PR introduces two complementary runtime changes: 1) an anticipatory kernel merge pass that detects adjacent microbatches with compatible kernel requirements and fuses their launch to avoid redundant kernel setup/teardown; and 2) an eager-output-drain path that proactively flushes already-computed tokens when downstream credit is likely to be available, reducing head-of-line latency for streaming consumers. Both changes are designed to be conservative by default and toggled under runtime flags for gradual rollout. Summary of changes:
- runtime/scheduler: add KernelMergePlanner which inspects next-N microbatches (configurable window) and proposes merge candidates when kernel config, device affinity, and memory footprint are compatible; new heuristics weigh predicted latency savings vs. extra queueing.
- runtime/launcher: implement fused kernel launch path with minimal synchronization and a fallback to existing per-microbatch launches.
- runtime/emitter: add EagerDrainController that monitors credit trends and preemptively emits completed token ranges; integrates with existing backpressure signals to avoid violating SLOs.
- runtime/kv_cache: prefetch alignment hints are emitted when kernels are merged so KV warmup can be shared between merged microbatches.
- runtime/metrics: new histograms for fused-kernel-duration, eager-drain-saved-ttfb, and merge-decision-rejection-reasons.
- tests/perf: new microbench harness replicating mixed small/large sequence workloads and a canary profile used to autotune the merge window.
- docs: runtime tuning guide section and examples for feature flags.

Observability notes: New metrics and logs are gated behind a runtime flag and emitted at low cardinality. Merge decisions are sampled (1%) in production to limit overhead; sampled traces include microbatch metadata and reasoning for auditability. Performance summary (staging canary):
- Mixed workload (60% short streams, 40% long streams) saw median streaming first-byte latency reduced by ~22% and P95 reduced by ~18% across a fleet of p3-equivalent instances.
- Tail reduction for interleaved small requests improved by ~28% due to reduced kernel churn.
- Cost per token is roughly neutral (slight improvement for workloads with >15% mergeable microbatches)
Safety and rollout plan:
- Feature flags: runtime.flag.enable_kernel_merge, runtime.flag.eager_output_drain, runtime.flag.merge_window_size. Default: disabled in production; enabled in canary for 2 weeks with sampling.
- Automatic rollback: if average P95 increases >5% over baseline for 30min, flag auto-disable.
- Gradual ramp: canary -> 10% of traffic -> 50% -> 100% with health gating after each step.
Backwards compatibility: no public API changes; internal event shapes in traces extended (backfilled by versioning).
Potential risks: over-aggressive merging can increase latency for long-running streams if merge buffering waits too long; we mitigate with a max-wait heuristic and preference for low-queue-time merges. CI/Codestate: One flaky test (emitter/credit-siphon-spec) required a test timeout bump and was rerun, all checks passed on the final commit. Please see commits for details and the canary report attached.
