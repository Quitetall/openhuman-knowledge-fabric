release_notes:
Adds a runway reservation controller that allocates short-lived runway credits per tenant to smooth sudden spikes and a lightweight fallback path to best-effort pools when runway is exhausted. Includes new telemetry (runway_seconds, runway_depletion_rate) and config knobs for operators.

description:
Motivation: Dedicated fleets occasionally experience short, high-frequency spike patterns that trigger emergency scaling and cross-tenant interference. Existing burst tokens are effective for single-shot bursts but do not account for recurring micro-spikes which cause oscillation. This PR introduces a lightweight ‘runway’ concept: a small, time-buffered reservation allocated per tenant that can be consumed continuously for short windows, enabling the autoscaler to absorb micro-bursts without immediate scale actions or draining warm pools.

Design summary: 1) RunwayReservationController: reconciles per-tenant runway balance (seconds * vCPU-equivalent) and top-ups based on observed admission rate and historical depletion. 2) Runway-aware admission path: admission checks consult runway balance first, decrementing in a streaming-safe manner; requests exceeding runway fall back to configured best-effort lanes instead of immediately failing or triggering scale-ups. 3) Depletion hedging: if runway depletion rate exceeds a configured threshold, the autoscaler receives a 'runway_pressure' signal which adjusts fast-path headroom and temporarily biases prewarming policies. 4) Telemetry and diagnostics: new metrics runway_seconds, runway_depletion_rate, runway_topup_events and runway_fallback_count; traces include runway decisions for sampled requests. 5) Operator controls: cluster-level defaults and per-tenant overrides; a conservative rollout plan with gated sampling and percent-of-tenants opt-in.

What changed (high level): - runtime/admission/runway_controller.go: reconciliation loop and in-memory ledger with epoched top-ups - runtime/admission/runway_store.go: durable checkpointing to etcd with backoff and compacting - runtime/admission/handler.go: admission path integration and fallback routing - autoscaler/signals/runway_pressure.go: emits signals consumed by scale decider - observability/metrics/runway.prom: metric definitions + dashboard snippets - docs/ops/runway.md: operator guide and rollout checklist - internal/tests/runway: unit + integration harness simulating spike patterns + load-tests updated to validate stability

Testing and CI: unit tests added for controller reconciliation and store failure modes; integration test simulates a tenant with micro-spike pattern and verifies reduced emergency scale events. CI initially showed a flaky integration test (integration/runway/reconcile_test) related to timing windows; fixed by switching to deterministic fake clock and adding tighter backoff expectations. All CI checks green at merge time.

Performance: internal mixed-workload benchmark (100 tenants, 30% bursty) shows ~12% improvement in p95 request latency tail and a ~35% reduction in emergency scale operations over the previous burst-token-only strategy. Memory and CPU overhead is small (controller steady-state ~60MB, negligible per-admission cost due to compact ledger).

Rollout plan: 1) Deploy controller disabled by default in staging; 2) Enable for 5% of tenants with conservative runway (3s equivalent) and monitor runway_depletion_rate + fallback_count for 72h; 3) Gradually increase to 25% and tune top-up heuristics; 4) Default-on for Dedicated clusters after 4-week observation and operator sign-off.

Migration and safety: runway store uses versioned keys; safe default when store is unavailable is 'no runway' which preserves pre-existing behavior (requests go to existing burst handling). There is an opt-out label per-tenant for immediate rollback.

Notes: this is an operationally-sensitive change — operations should watch the new metrics and the autoscaler fast-path behavior during rollout. See docs/ops/runway.md for full checklist.
